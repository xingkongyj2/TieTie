# 会话独立记忆系统

每次新建双人空间，创建一个新的 Qoder Session 和一个独立 Memory Store。即使同一对成员解绑后再次绑定，也从新空间开始。当前有效绑定的重复提交是幂等操作；进程重启恢复已有空间，不清空记忆。

## 固定 JSON 模板

模板位于 `backend/internal/memoryspace/templates/`，通过 Go `embed` 编译进程序。包含用户要求的五种模板，另补充习惯/长期行动和记忆维护规则。所有模板有 `schemaVersion`，仓库映射保存 `templateVersion`。

| 路径 | 保留的字段与用途 |
| --- | --- |
| `profile/users.json` | 两位成员真实 userId、姓名、昵称、性别、生日、简介、头像、作息、饮食、生活偏好、禁忌、爱好、职业、沟通偏好 |
| `agreements/shared.json` | 群聊 ID、空间 ID、成员、默认群规则、共享约定 |
| `tasks/todo-board.json` | 事项、截止时间、状态、发布人、被提醒人；另有提醒/定时任务状态与确认完成人 |
| `context/realtime.json` | 类型、内容、生成时间、过期时间、是否过期的定义 |
| `rules/assistant-behavior.json` | 身份、原则、功能规范、禁止行为、异常处理、speakingStyle 当前说话方式 |
| `profile/habits.json` | 稳定习惯、长期计划、周期/条件、偏好时间、来源、确认状态 |
| `rules/memory-policy.json` | 读取、归属、更新、删除、存储策略、有效期规则 |

A/B 按 userId 升序固定。“自己/对方/我们”只用于展示；实际记录用 userId，不会随发言人交换。初始化填真实 ID、注册名、账号已保存的小档案、时区与代码固定规则；未提供的昵称/作息/喜好不猜测。小档案按真实账号保存在 user_profiles，不能把浏览器内的演示档案或其他账号的资料上传成当前用户事实。

这7个文件同时规定所有运行时数据的分类与结构，不只是目录入口。新增数据写入对应模板的数组/人物字段；数据量增加后按同名模板分页，所有页面的 type 和主字段保持相同。云端路径与内容类型都有白名单校验，不再创建观察记录、单条事实、提醒历史索引或独立协议等新类型。初始空字段不能解释成当前用户没有偏好，读取时需检索该模板的相关分页。

## 初始化时序

1. 校验双方当前未绑定；已有当前绑定直接返回。
2. 生成随机空间 ID，创建新的独立仓库，不查询同名历史会话或配对仓库。
3. 渲染、校验并写入全部七个 JSON 模板。
4. 创建 Session，挂载这一仓库的只读资源。
5. 仓库改名为 `TieTie-<实际 Session ID>-memory`，保留仓库 ID、归属元数据和记忆条目；将公共信息中的群聊 ID 补成实际 Session ID。私密分支的仓库同样包含其独立 Session ID。
6. 在单一数据库事务中发布绑定、仓库映射、模板索引与双方已保存档案的当前事实及分页。云端模板在发布前已包含双方档案；事务再次读取最新账号资料，将并发期间的修订加入持久化同步队列。

明确失败或并发绑定落败时清理本次多余会话及仓库；不能影响旧空间。创建 Session 的网络结果不明确时保留该仓库供核实，避免删除可能已被云端挂载的资源，不发布未确认绑定。清理失败记录资源 ID。当前没有云端创建幂等键或后台孤儿资源扫描，进程在远程创建与本地提交之间崩溃也可能留下未绑定的云端资源。

新建空间要求 服务端 V2 协议（当前默认固定为 2）和 `QODER_MEMORY_ENABLED` 开启，否则返回 `memory_required`，避免成功创建一个没有记忆的空间。已有空间不重置、不合并；升级会将已有记录归类到同一套模板，成功同步替代页后清理旧格式文件。私密分支初始化也准备同样7个模板，事实及历史独立保存。

## 我的小档案同步

`GET /api/account/profiles` 只返回登录用户和当前绑定另一成员的档案，`PUT /api/account/profile` 仅修改 JWT 对应用户，不能由请求体指定其他身份。保存生日、性别、爱好、简介与头像时，账号表、当前会话 `profile/users.json`、稳定 `account_profile` 事实及其模板分页在同一事务更新；同步失败保留队列，重启后继续。修改也同步到该绑定已有的私密分支，但不修改已退出会话的历史档案。新建共享或私密会话从账号资料初始化；未绑定时也可先保存档案。

同一内容重复保存不增加事实修订；更正历史留在数据库。清空生日、简介或爱好列表会写入当前空值，不能以旧档案恢复。同步只更新小档案字段，保留其他已有作息、饮食、职业与来源信息。AI 开始下一轮成员对话前，按固定的最多三个记录同步待更新的人物档案根文件及双方当前档案事实，避免读取旧挂载文件；同步失败时保留已保存资料及重试任务。

## AI 与数据库各自负责什么

| 数据 | 长期正文策略 | 责任 |
| --- | --- | --- |
| 称呼、个人作息、饮食、生活偏好、禁忌、纯对话习惯 | `database_and_memory` | 数据库保存事实、归属、来源、更正历史与页面位置；云端按人物/习惯模板合并分页，AI 检索并使用 |
| 共同约定、地址、分工、需程序/界面查询的长期计划 | `database_and_memory` | 本地存业务正文，同时同步云端供 AI 理解 |
| 普通提醒、纪念日、贴贴提醒与执行历史 | 数据库 + 云端 | 数据库负责具体触发时间、投递、取消、事项完成；云端保存事实用于理解上下文 |
| 天气、快递、取餐码等临时事实 | 数据库 + 云端，必须有有效期 | 本地判断有效期、退出检索、排队删除云端当前条目 |
| 固定模板/规则 | 数据库 + 云端 | 代码版本管理、初始化；规则补充不能覆盖服务端协议 |

旧控制请求中的 `memory_only` 作为兼容值接受，服务端统一持久化事实，以支持有界分页、可靠更正和完整历史；同步成功后只清空临时 pendingContent，不清空事实正文。控制任务完成后仍清除临时输入。空间内双方均可读当前空间的记忆，`self` 表示事实归属，不表示私聊。双方不再绑定后无法通过当前会话接口读取旧空间。

## 同模板分页与结构化字段

```json
{
  "type": "save_memory",
  "key": "sleep_schedule",
  "category": "habit",
  "scope": "self",
  "storage": "database_and_memory",
  "content": "本人通常23点睡觉",
  "data": {"schedule": "23:00", "confirmation": "本人确认"}
}
```

后台补充真实 `ownerId`、`sourceUserId`、`sourceRequestId`、`generatedAt`、`updatedAt`、`expiresAt` 与 `schemaVersion`。用户或模型不能指定仓库 ID 或任意路径。

| category | 条目目录 | data 字段（值为字符串） |
| --- | --- | --- |
| `profile`（默认） | `profile/users/YYYY-MM/NNNNNN.json`，字段 users[].entries / sharedEntries | name / nickname / schedule / diet / lifePreference / taboos / hobbies / profession / communicationPreference |
| `habit` | `profile/habits/YYYY-MM/NNNNNN.json`，字段 entries | content / schedule / preferredTime / confirmation |
| `agreement` | `agreements/shared/YYYY-MM/NNNNNN.json`，字段 agreements | content / confirmation |
| `realtime` | `context/realtime/YYYY-MM/NNNNNN.json`，字段 entries | category（天气/快递等具体类型） / content |
| `behavior` | `rules/assistant-behavior/YYYY-MM/NNNNNN.json`，字段 additions | content / confirmation |

`agreement`、`behavior` 必须为共享 scope。个人稳定事实以本人明确陈述或角色信息页手动补充为依据；共同约定、行为追加需要双方确认，冲突时暂停相关执行。角色信息页的说话方式是已授权的界面设置，一方保存即可更新当前空间，不额外询问双方确认。确认状态由 AI 根据有来源的对话判断，目前没有单独的双人审批表，不能把 AI 对共识的理解等同于独立审批系统。

更正时传已有 `memoryKey`，后台验证同一会话、归属、分类，更新原逻辑事实，避免因为动作 key 改名生成重复条目。页面按条数和字节容量分配，普通更正只更新所在页；容量不足时移入下一页并更新旧页，其他事实保留。旧版本存入 memory_revisions，可以 read_memory 指定 revision 读取，旧版本不作为当前偏好。先读取原文，保留未变的相关字段。一位成员不能修改或删除对方的个人事实，固定模板和提醒投影不能通过普通记忆操作删除。所有云端更新带内容 hash 条件；数据库 revision 防止旧同步回执覆盖新版本。

AI 在回答与建议前主动检索相关偏好和习惯；本人日常聊天明确提供的稳定习惯、爱好、职业及工作节奏应积累为记忆，无需每次要求“记住”。临时情绪、假设、玩笑不长期保存。所谓“越用越聪明”是积累事实、及时更正并检索应用，模型参数没有被训练。

## 角色信息页的对方印象

`GET/POST /api/qoder/sessions/{id}/partner-impression` 仅允许当前绑定双方访问。目标成员由登录身份与绑定确定，不接受任意目标 ID。POST 接收 `text`（1～2000字）和 `requestId`（幂等键），补充合并到 `profile/users/YYYY-MM/NNNNNN.json` 的目标 users[].entries，归属对方、来源为提交者、标注 `sourceType=role_supplement` 和 `confirmation=已确认`，直接作为对方的个人信息和偏好，无需本人再次核实，使用 `database_and_memory`。云端暂时失败时本地持久化并返回 pending，后台继续同步。

印象只使用目标成员最近80条有效 profile/habit 事实及当前共享会话最近80条用户发言；私密会话及历史私密消息、AI 自己的概括均不作为依据。生成时读取真实 JSON 正文，包括尚待同步的补充；不使用前端演示档案。独立临时云端会话不挂载仓库、不向聊天插入隐藏轮次，完成后删除。AI 省略基础身份字段，重点概括习惯、爱好、职业和生活/沟通偏好，保留本人陈述与角色页补充的来源，两者均可作为事实依据，不凭空填充性格。

印象生成明确区分阅读者 viewerUserId 与目标 targetUserId，目标用第三人称“TA”，不把对方称为“你”；单次提醒请求不能推断性格或长期习惯。数据库按空间与目标缓存印象和来源 hash（包括生成规则，规则修正后旧缓存会重新生成），补充或共享聊天/记忆变化后在页面打开时排队更新。结果发布会校验来源版本，旧生成结果不能覆盖新补充。失败需点击重试，页面轮询不会反复生成；服务重启恢复中断任务。正文及聊天输入有长度预算，这不是全历史穷举；更早的稳定信息通过长期事实积累参与后续生成。印象仅是派生展示，不反向成为长期事实。

## 有效期与提醒事实

`realtime` 必须用 `database_and_memory` 并提供未来的 RFC3339 `expiresAt`。所有数据库过期时间统一 UTC，用户时间及 AI 的 `currentTime` 使用上海时区。初始 `expired` 是计算字段定义，实际是否过期以当前时间与 `expiresAt` 比较为准，不能相信旧的“未过期”标记。

到期后立即从索引退出，`read_memory` 拒绝读取；后台按有效期索引、有限批次把内容清空并创建云端删除任务。网络失败仍重试，但不得继续将云端残留当成当前事实。提前取餐、签收或撤回可用 `delete_memory` 删除。删除当前条目不等于物理清除云端历史版本。

任务板在提醒变更事务中更新。`status` 表示提醒本身的 `pending/completed/cancelled`：已提醒或手动完成都计入 completed。`deliveryStatus` 和 `taskStatus` 保留实际执行事实，`activityStatus` 单独表示实际事项是否被确认完成，不能因 AI 已提醒就断言成员已经做完事项。提醒页仅将 pending 计入待完成，其余归入“已完成”列表；取消仍保留 cancelled 事实并显示黄色标签，已提醒显示绿色标签。手动取消时将取消状态和 AI 确认队列原子保存，按会话与提醒 ID 幂等，私密确认留在私密会话。已结束提醒不能取消或重新触发。启动时按实际执行状态修正旧索引和对应云端页面，只更新受影响的页，不重写已修正的历史。`tasks/todo-board.json` 最多展示16条当前待办与8条近期记录，展示上限不影响历史保存。

所有提醒的完整事实按上海时区的创建月份保存在 `tasks/todo-board/YYYY-MM/000001.json` 起的连续分页，每页最多16条；包括完成与取消记录，无历史保留期限。数据库仍保留全部提醒及原有执行字段。`reminder_history_locations` 为每条记录分配固定月/页位置；状态变化只更新所在页，无需重排或重写整个月。`reminder_history_months` 在事务中维护追加计数，不为每次新增扫描月份全部记录。不再生成随机分桶页和单条 `shared/reminders/<id>.json`。

根模板 `tasks/todo-board.json` 的 history 字段列出最近12个有记录的月份、记录数及页数，更早月份的完整文件仍保留，可直接按目录检索。AI 的默认上下文仍有界，按问题读取相关月份/页。到期消息读取实际云端归档页后，按 reminderId 只提取本条完整事实，避免将同页其他提醒带入通知。

分页、当前待办与近期记录使用对应复合索引，普通更新最多读取16条归档记录、17条待办位置、8条近期位置；相同内容不重复入队。文档有96 KiB大小保护，低于客户端允许的单条100 KiB写入上限。这里的上限是应用客户端限制，不是云端总体容量承诺。

启动迁移按200条批次为旧记录建立固定位置，并按受影响页生成完整归档。对应模板分页同步成功后，旧单条文件与随机分桶页才可进入云端删除队列；同步失败、旧版本回执或进程中断不会提前删除旧副本。数据库原始提醒不删除；无法与数据库记录关联的旧文件保留。私密记录独立归档，实际通知公开后，仅该条记录另外进入共享历史。已退出空间的旧云端仓库确实不存在时，从数据库完整归档重建独立仓库并重新同步；当前有效绑定的挂载仓库不会通过此流程替换。

长期习惯或周期计划可以记住；当前执行器只支持一次性提醒。每天/每年计划不会因写入记忆而自动调度，不得声称已建立周期任务。纪念日和贴贴如有明确时间，使用统一 create_reminder 链路。

## 纪念日与首页展示

用户明确要求添加纪念日时，AI 使用 `save_anniversary`，提供名称、完整 `YYYY-MM-DD` 日期和类型（在一起、生日、结婚、初次相遇或其他纪念日）。服务端将真实记录、幂等回执和记忆待同步内容原子保存，成功回执后 AI 才确认。更正使用现有 `anniversaryId`，保留原记录与置顶状态，不新建重复纪念日。日期记录本身不创建定时提醒。

纪念日存入 `anniversaries`，长期事实按 `entryType=anniversary` 合并到 `agreements/shared/YYYY-MM/NNNNNN.json` 的 agreements 数组；沿用原有模板与修订历史，不增加新的云端数据类型。共享与私密会话隔离。每轮 AI 只收到最多16条记录及可能额外的一条置顶记录，更多历史通过同模板分页检索。

删除或取消纪念日使用 `delete_anniversary` 和真实 anniversaryId：先在数据库事务中删除卡片记录，同时保存幂等删除回执与记忆 tombstone，提交后再同步云端原模板页。云端失败时卡片仍已移除，回执明确 databaseStatus=deleted、memoryStatus=pending，后台继续重试；不能仅删除记忆或只口头确认。兼容旧模型对纪念日事实发出的 delete_memory，将其转为同一数据库删除链路。普通 save_memory 不能直接改写纪念日事实。删除前的记录快照与记忆修订留在本地历史，不再作为当前日期使用。删除置顶项恢复默认空间起点卡。

启动时按200条批次修复旧版“记忆已删除、卡片记录仍在”的情况，仅匹配同会话、同绑定版本、原纪念日逻辑路径的删除标记，保留修复回执。列表接口返回 deletionCursor，客户端以 afterDeletion 查询最多200个 removedIds，移除已经加载的所有页中的对应记录；超过该上限时 resetRequired 要求重载第一页，避免无限删除索引。删除了分页边界记录时，服务端用删除快照里的原始创建时间与 ID 继续读取历史。背景刷新以请求序号丢弃旧响应，防止恢复已删除卡片。

`GET /api/qoder/sessions/{id}/anniversaries` 返回最多50条记录、游标、当前置顶项和绑定的真实创建时间。两位成员都能通过 PATCH 置顶或取消置顶，事务和数据库唯一索引保证同一会话只有一个置顶项；替换置顶时原条目与新条目的记忆一起更新。首页“小纪念”展示置顶项，未指定其他纪念日置顶时，默认置顶“专属空间开始”及上海时区的实际日期和时间，不使用模拟在一起日期。默认起点卡始终保留，默认置顶在列表首位；置顶其他条目后也可通过起点卡按钮恢复。所有卡片使用相同布局与蓝色风格，起点使用圆形背景，其他纪念日按类型/名称匹配不同图形，适用于情侣与朋友。

## 数据量与查询边界

- 仅允许7种模板及其分页；事实按月合并，每页最多8条，预留内容字节预算80 KiB；提醒每页最多16条。所有页面都有96 KiB文档大小保护。不会每个事实生成一个新类型文件，也不会在一个文件无限追加全部历史。
- 数据库查询的索引包含固定模板和最近事实，总计最多 100 条；发给 AI 时，首次只提供近期事实索引，后续只发送变化和移除的索引键。固定模板路径已在协议中说明，不逐轮重复。已挂载仓库可按目录检索更早的相关事实，索引未显示不等于没有记忆。
- 固定传输规则在首次消息时保存在 `rules/assistant-behavior.json` 的 instructions 字段，数据库和当前会话的独立云端仓库同步保存；云端人设保持不变。`conversation_protocols` 持久化已被云端接受的协议摘要、绑定版本和上下文快照，避免重启后每轮重发。
- `GET/PUT /api/qoder/sessions/{id}/assistant-settings` 按真实绑定读写当前说话方式，仅允许 warm（温柔陪伴）、playful（调皮一点）、concise（简单直接）。根模板 speakingStyle 保存当前选项、名称与固定风格说明，保留已有 instructions 和其他行为规则；稳定 behavior 事实保留更正历史并沿用该模板分页。新空间默认温柔陪伴，同一空间的独立私聊继承该设置；不同空间不互相继承。保存时尝试同步云端，失败保留数据库和 outbox；下一轮服务器信封 assistantStyle 仍提供最新风格，后续仅在风格改变时发送。风格只影响自然语言，不改变事实、权限、静默模式和执行回执规则。
- `GET /api/qoder/sessions/{id}/memories?category=habit&after=<memoryKey>` 返回当前有效空间的元数据，每页最多 100 条及 `nextCursor`，正文不随列表下发。游标按 ID 排序，避免大 OFFSET。客户端未来可据此实现管理页面；本次未新增记忆管理 UI。
- 本地索引覆盖 session/kind/update、session/category/id、session/id、expiresAt；事实页面位置覆盖 session/category/month/page；提醒位置覆盖 session/month/page/position、session/status/dueAt/id、session/createdAt/id。
- 定时、控制、同步沿用有界批次和可恢复 outbox。云端记忆成功后才确认成功，失败回执说明云端待重试。
- SQLite 当前适用于单实例，分页和索引避免无限上下文与大文件；这不是多副本或线上大规模吞吐量保证。
